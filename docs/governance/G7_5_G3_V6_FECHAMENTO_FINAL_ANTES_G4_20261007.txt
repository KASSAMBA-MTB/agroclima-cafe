3. GRADE COMPLETA
==============================================================================

A resposta válida do G4 deve representar uma grade completa:

    14 variáveis
    ×
    48 timestamps
    =
    672 registros

Não é permitido:

    variável com 47 registros;
    variável com 49 registros;
    timestamp ausente;
    variável ausente;
    linha descartada por MISSING.

Um registro MISSING possui:

    value = NULL
    value_status = MISSING

A ausência de uma linha é diferente de MISSING.

Ausência de linha:

    falha de contrato.

Linha MISSING:

    dado canônico válido dentro do contrato.

6. UNIT_MISMATCH
==============================================================================

Se uma variável estiver presente com unidade diferente da unidade esperada:

    UNIT_MISMATCH

A resposta deve ser rejeitada antes do content_sha256.

Exemplo:

    wind_speed_10m
    recebido: m/s
    esperado: km/h

Resultado:

    CONTRACT_PROFILE_MISMATCH
    + UNIT_MISMATCH

Não tratar como:

    SingleRunContentConflictError

Mudança de unidade é mudança de contrato.

8. HORIZONTE TEMPORAL
==============================================================================

A evidência consolidada do G7.4/P4.2 mostrou:

    primeiro timestamp = início do RUN
    48 timestamps
    passo horário
    último timestamp = run_datetime + 47 horas

Portanto:

    forecast_datetime[0] = run_datetime

e:

    forecast_datetime[n] = run_datetime + n horas

para:

    n = 0 ... 47

Não utilizar somente a contagem 48 para validar o horizonte.

==============================================================================
9. PRIMEIRO TIMESTAMP
==============================================================================

    run_datetime

Não é:

    run_datetime + 1h

A validação deve comparar o primeiro timestamp recebido com o run_datetime
do ModelRun.

Se diferente:

    HORIZON_MISMATCH

==============================================================================
10. PASSO TEMPORAL
==============================================================================

    1 hora

Para cada par consecutivo:

Qualquer:

    salto;
    duplicação;
    intervalo irregular;
    timestamp deslocado;

deve provocar:

    HORIZON_MISMATCH

antes do content_sha256.

15. CONTENT SHA256 — FINALIDADE
==============================================================================

    status;

raw_sha256 não decide conflito.

==============================================================================
16. SERIALIZAÇÃO DO CONTENT SHA256
==============================================================================

Cada ForecastRecord será serializado como:

    forecast_datetime|variable|unit|value|value_status

Ordenação:

    forecast_datetime ASC
    variable ASC

A ordenação de variable é por codepoint do Python, sem locale.

Encoding:

    UTF-8

Separador de campos:

    |

Separador de registros:

    LF (
)

O payload final termina com LF.

==============================================================================
17. DATETIME DO HASH
==============================================================================

O formato é estritamente:

    %Y-%m-%dT%H:%M:%SZ

Exemplo:

    2026-10-03T00:00:00Z

Não aceitar variações como:

    2026-10-03T00:00Z
    2026-10-03T00:00:00.000Z

na serialização canônica.

O datetime deve estar normalizado para UTC antes da formatação.

==============================================================================
18. FORMATO NUMÉRICO
==============================================================================

Para NUMERIC:

    format(value, ".17g")

Normalização obrigatória:

    -0.0 -> 0.0

Assim:

    0.0
    -0.0

produzem a mesma representação canônica:

    0

Não usar:

    str(value)

Não usar locale.

==============================================================================

==============================================================================

    format(0.1, ".17g")

    format(0.0, ".17g")
        -> '0'

Esses valores são vetores de teste do serializador.

==============================================================================
32. CONCORRÊNCIA
==============================================================================

Duas ingestões simultâneas podem disputar a mesma UNIQUE.

A estratégia correta é:

1. tentativa de criação dentro de atomic;
2. IntegrityError é capturado FORA do bloco atomic;
3. iniciar nova transação para reler o ModelRun;
4. comparar content_sha256;
5. igual -> idempotente;
6. diferente -> conflito;
7. IntegrityError de causa diferente -> propagar.

Não tentar consultar o ModelRun dentro de uma transação marcada como rollback.

Alternativamente, poderá ser usado savepoint interno, desde que o resultado
seja equivalente.
